# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`seancheren.com` — a small multi-user app suite (Reminders · Calendar · Notes · Habits · Chat · Aki's Bookshelf) in plain PHP on NearlyFreeSpeech.NET. No framework, no build step, no database, no dependencies. Each app is essentially one self-contained `index.php` that renders its own HTML/CSS/JS inline and posts back to itself.

## Commands

```sh
php -S 127.0.0.1:8787 -t public          # local server; apps at /reminders/, /calendar/, …
find public lib -name '*.php' -exec php -l {} \;   # lint everything (no test suite exists)
./deploy.sh --dry-run                    # preview the deploy
./deploy.sh                              # lint, then rsync to the live site
```

`deploy.sh` is one-way (Mac → server) and deliberately never sends `lib/config.php`, never touches `/home/protected/data/`, and never uses `--delete`. The Mac is the source of truth; if anything was hand-edited on the server, `rsync` it back down before deploying (see README).

Local login: users come from `lib/config.php` (gitignored; copy `lib/config.sample.php`). Local data lands in `./data/` and is unrelated to live data.

## Layout and the web-root boundary

- `public/` → server `/home/public/`. Anything here is URL-reachable.
- `lib/` → server `/home/protected/lib/`. Shared code, never served.
- `data/` → server `/home/protected/data/`. JSON storage, never served, gitignored.

Every app page starts by locating `lib/` at either `__DIR__ . '/../../lib'` (local) or `/home/protected/lib` (server) — copy that preamble verbatim when adding a page.

**The public top-level pages** (Home `/`, `projects/`, `about/`, `contact/`) are the site's marketing front, not part of the app suite: no login, no tab bar, no `chrome.php`. They share their own chrome through `lib/site.php` — `site_nav($active)` renders the pill nav and `site_page($active, $title, $bodyHtml)` wraps a page in the full HTML shell (dark theme echoing Reminders: `#111`/`#eee`/`#34d399`). Add a new static page by calling `site_page()` and adding its slug to the `$links` map in `site_nav()`.

## Core mechanics

**Storage.** All data goes through `store_read()` / `store_write()` (`lib/store.php`), which encrypt with AES-256-CBC under an `ENC1:` prefix. Reads transparently accept legacy plaintext JSON and re-encrypt on next write. Never `file_get_contents` a data file directly. Key comes from config `data_key` or an auto-generated `data/.datakey`.

**Per-user files.** `user_data_file($dir, $base, $user = null)` → `data/<base>-<user>.json`, defaulting to the signed-in user. Bases in use: `reminders`, `notes`, `events`, `calendars`, `calprefs`, `folders`, `habits`, `books`, `booknotes`, `shares`. `chat.json` and `token-<user>.json` are handled with hand-built paths.

**The clock.** `lib/auth.php` sets `date_default_timezone_set()` from config `timezone`, defaulting to `America/Chicago`. The server keeps UTC, so without it "today" turns over in the evening and the calendar advances a day early. Every page reaches this through `auth.php`.

**Auth.** `require_login('Area')` (`lib/auth.php`) — session-based, plaintext user⇒password map in config, `hash_equals` compare. One session covers the whole suite. A password the user changes themselves lands in the encrypted `data/passwords.json` and wins over the config entry, because `config.php` is hand-kept on the server and never deployed — delete that file to fall back to config. `require_login()` also seeds `$_SESSION['csrf']` and answers the settings window's `change_password` POST, so no app has to wire it up. **Anyone can sign up from the login page**: `signup_handle()` takes a username, a valid email and a password, emails a four-digit code through `mail_send()` (`lib/mail.php` — an authenticated TLS SMTP session when config names `smtp_host`, plain `mail()` otherwise, with either failure logged to `data/mail.log`; `php tools/mailtest.php you@example.com` sends one test message), and parks the half-made account in `data/signups.json` for fifteen minutes (five wrong codes and it's gone). Only when the code comes back does it land in `data/accounts.json`, which `app_users()` merges with the config accounts — config wins on a clash. Nothing else in the suite is per-account gated beyond its own data files, so a new account is an empty suite; sharing stays sean⇄aki. Chat is deliberately public (no login). **Sending is currently switched off**: `signup_send_code()` has the `mail_send()` call commented out, logs a "would have emailed …" line instead, and every sign-up takes the fixed `SIGNUP_CODE` (`1234`) — so anyone who finds the login page can make an account. Turning real mail back on is un-commenting those two lines and restoring `random_int` in `signup_handle()`, once the SMTP credentials are in the server's `config.php`. `public/dev/` is a legacy standalone login unrelated to the rest.

**Mutations.** Every write is POST with a CSRF token from `$_SESSION['csrf']`, checked with `hash_equals`, then either a redirect (POST→redirect→GET) or, for AJAX callers, a `json_encode` response. AJAX posts send `X-Requested-With: XMLHttpRequest` and the handler echoes back the fresh authoritative state (e.g. the whole calendar list) rather than a bare `ok`.

**Sharing (sean ⇄ aki only).** `lib/sharing.php`, which also owns the share window itself (`share_modal_html/styles/script`, `share_handle_set`). It opens from the **Settings `⋮`** in every app that has a partner (Reminders, Calendar, Notes) — the centred "Share" button between Change password and Done — and asks the page for the current lists through `window.shareData()`. It lists three kinds: calendars, reminder folders and note folders (`SHARE_KINDS` maps each kind to its bucket). Sharing is opt-in per item: nothing is visible to the other person until it's ticked. Nothing is ever copied: `shares-<user>.json` has three buckets — `calendars` (ids), `folders` (reminder folder names) and `notes` (note folder names) — and the reader loads the *owner's* file directly. Shared folders appear in the picker as `@<partner>:<Folder>`; when that view is active, reads *and* writes go to the partner's file, but structural edits (add/delete section, delete folder, reorder) are refused with 403. Reminders and Notes share the same shared-folder machinery — `shared_reminder_folders()` / `shared_note_folders()` validate a partner's shared list against what they still own on every read. Always re-check membership before touching a partner's data.

**Recolouring a partner's shared folder.** Each person can recolour how the other's shared folders show *in their own picker*, using the lighter shared-palette variant (`app_palette($app, true)`). The override lives in the viewer's own `folders-<user>.json` under `colors.shared[$type]`, keyed by the full `@<partner>:<Folder>` view key, so it never touches the owner's data. `folder_shared_color()` resolves the colour: the viewer's override first, then the owner's own colour, then a shared-palette default by position. The recolour swatch is a read-only row under "Shared with me" in the folder manager; its `set_folder_color` post routes to `folder_shared_color_set()` when the name parses as a shared key.

**Lists with sections.** Reminders, notes, habits and book notes store section headers as rows in the same list (`['type' => 'section', …]`), guarded by an `is_section()`-style helper. Stored order is drag order; drag-reorder posts the new order via AJAX. A section header carries a blank drag-handle slot where it has nothing to drag (Reminders' two permanent groups, every Notes and book-note section), so its name starts level with the rows under it and with every other section's. Reminders additionally *displays* each group undated-first then by date, using stored order only to break ties — so dragging within a Reminders section is largely cosmetic, while dragging between sections and reordering sections still does what you'd expect.

**Habits rename in place.** A habit's name is editable by **double-click**, **long-press**, or a single tap while the Edit pencil is on — the label swaps for a field that posts `rename_habit` over AJAX (Enter or blur commits, Escape reverts), so the grid never reloads and nothing scrolls. Its sections still rename through `section_title_html()` like everywhere else.

**Renaming a section.** In edit mode a section's name is a field (`section_title_html()` / `section_rename_styles()` / `section_rename_script()` in `lib/chrome.php`): Enter or leaving it posts `rename_section`, Escape puts it back. Reminders, Notes and habits answer that action; `section_rename()` in `lib/util.php` moves the header and re-points every row that named it, refusing an empty or already-taken name. Habits key their sections by id, so they rename in place instead.

**Permanent groups.** Reminders has two sections the user can't create or delete: `DEFAULT_SECTION` (`Reminders`, the ungrouped catch-all, stored as `section => ''`) and `CALENDAR_SECTION` (`Calendar`, from `lib/util.php`). An *undated* item in the Calendar group rides along on the calendar under today, every day, until it's ticked off — the Calendar page and `feed.php` both special-case it, and it must not be flagged `rolled`/overdue, since it isn't late. Both groups are filtered out of the user's own section list on render and rejected by `add_section` / `delete_section`.

**Empty sections in a folder view.** A section with no rows under the viewed folder is marked `.folder-empty` and hidden by CSS, not skipped server-side — it has to stay in the DOM so that a section you just created (which has no rows yet) is visible while editing instead of appearing to vanish. Anything that hides a group conditionally should hide it the same way, since the view is remembered across visits and `All` is usually *not* what you're on.

**Adding to Reminders.** Notes works the same way — its `+ Note` button is gone too. There is no New-item window in Reminders any more. Each section header carries a `+` immediately to the *right* of its name (in Notes it fires `add` directly; in Reminders it reveals an inline row) posting `action=add` with that `section`; the server runs the typed text through `parse_when_from_text()`. The delete `×` is pushed to the far right (`margin-left: auto`). New reminders, notes and sections are prepended, so they land at the *top* of their list/section. A collapse chevron (`section_collapse_button()`, `lib/chrome.php` — a small `>` that points down when open, right when collapsed) sits at the left of the name; tapping it folds the section (remembered per page in `localStorage`, hidden in edit mode where the drag handle takes that slot). **Subsections:** in edit mode every reminder and section carries a `‹ ›` pair (`indent_controls()`) that outdents/indents it; the level is stored as `indent` (0–4) via an AJAX `set_indent` and rendered as `padding-left` (via a `--ind` CSS var) so the content shifts right while the delete `×` stays pinned to the right edge.

**The outline drag model.** The indent levels are read as an outline: **level 0** is a section, **level 1** is a subsection *or* a reminder sitting under a section, one more indent again is a sub-subsection or a sub-reminder. Dragging follows from that, and nothing moves until the drop — a single `.drop-line` (a zero-height accent border, an `<li>` inside a row list and a `<div>` between blocks) is the only feedback, because live-shuffling the real rows made it impossible to see what you were about to get. **Level 0 travels as a block**: `blockOf()` walks forward from the section over every following group with a deeper indent, so a section's subsections and rows always come with it, and it can only land between other level-0 blocks — never inside one. **Level 1 goes anywhere among level-1 things**: a reminder or a subsection can be dropped between any two rows in any list. Dropping a *subsection* among rows splits that list — everything from the line to the end of the list becomes its, which is exactly "up to the next subsection or section", since a list only ever holds one section's rows. Because the `.folder-block` wrapper is the parent in the All view, a block can't wander into another folder. `topOf()`/`isTop()`/`lvlOf()` read the level straight off the `--ind` custom property, so the DOM stays flat and there's no real tree to keep in sync. Creating an *event* or *note* now only happens in the Calendar and Notes apps.

**Repeats** (`lib/util.php`). A reminder or event may carry `repeat => ['n' => 2, 'unit' => 'day'|'week'|'month'|'year']` — "every 2 weeks"; absent or null happens once. There is only ever the one stored row: `repeat_dates($start, $rep, $from, $to)` expands it over whatever window the reader is drawing, so the Calendar expands across the month it renders and `feed.php` across its 21 days — both places need changing together, as ever. Month and year steps keep the day of the month and clamp it (the 31st repeats as the 30th, the 28th…) rather than sliding into the next month the way `strtotime('+1 month')` does. **Ticking a repeating reminder rolls its `due` to the next occurrence instead of marking it done** (`repeat_next()`, in both the Reminders app's `toggle` and the Calendar's `toggle_reminder`), so the row always sits on the next date it owes — and, like every dated reminder, an overdue one still shows on today. Notes don't repeat.

**Text parsing** (`lib/util.php`). `parse_time_from_text()` pulls `2pm` / `2:30 pm`; `parse_date_from_text()` pulls `m/d`, `m/d/yy`, `m/d/yyyy` (bare `m/d` = next occurrence). `parse_when_from_text()` runs both and returns `[text, date, time]`. Date parsing is slash-only and US-order so it can't wander into other numbers, but it can't distinguish a date from a fraction — `2/3 cup` parses as Feb 3. An explicit date/time field from a form always wins over the parsed one. Adding *and* editing an item on the Calendar read the text the same way, so retyping "Vet 8/3 2pm" on an existing reminder moves it. Reminders carry an optional `time` alongside `due`.

**Note bodies are HTML** (`lib/richtext.php`). Notes and book notes are edited in a `contenteditable` (`.rt-body`) mirrored into a hidden `input.rt-value` named `body`, so autosave still posts an ordinary field. Everything is stored through `rt_sanitize()` — a DOMDocument allowlist (`b i u strong em blockquote ul ol li br div p span`, plus `class` only when it matches `rt-*`) — because the body is rendered rather than escaped. `rt_body_html()` spots a body with no tags at all as one of the old plain-text notes and escapes it, so nothing written before this needs migrating. `rt_toolbar_html(true)` adds the bookshelf-only `+✏️` window (next to the quote button) that inserts a quote, a note about it, a page number and an optional date stamp. The quote button toggles: pressing it inside a quote lifts *only the caret's line* out by hand — `formatBlock('div')` doesn't reliably strip a blockquote — and lines are found either as block children or as runs between `<br>`s, since Enter produces one or the other depending on the browser.

**Folder blocks in the All view.** When "All" spans more than one folder, Reminders and Notes wrap each folder's sections in a collapsible `.folder-block[data-folder]` headed by `.folder-head` — `folder_collapse_button()`, the folder's name, its colour dot, and a short right-aligned rule. `folder_collapse_script()` (`lib/chrome.php`) remembers the folded ones per folder in `localStorage`, keyed separately from sections so the two never collide. **Notes derives the folder list from its notes as well as its sections** (`$folderOrder`), because a folder can hold nothing but loose notes and still deserves a heading — deriving from section rows alone showed nothing. It also renders a per-folder copy of the permanent "Notes" catch-all inside each block (`render_note_default_group()`), so a note added from that `+` lands in that folder. Reminders does *not* do this: its two permanent groups (`Calendar`, `Reminders`) are genuinely global and stay outside the folder blocks, so a reminders folder with no sections of its own gets no heading.

**Folders** (`lib/folders.php`) are a separate per-user filter; `General` always exists and is undeletable. Both apps pick one from `render_folder_pick()` — a round colour button on the *right* of the top bar, by the `⋮`, dropping a menu grouped by owner, the same shape as the Calendar's calendar picker. **Manage folders** is the last row of that dropdown (`$manageLabel`, id `folderMgr`) rather than a button of its own; the Calendar's picker carries a matching "Manage calendars" row. Folders carry a colour from the per-app palette (`app_palette('reminders'|'notes')` in `lib/palette.php` — blue/red/green/orange/purple/grey, each app at its own shade, partner shares one step lighter), stored under `colors` in the same file, defaulting by position so a new folder is distinct straight away; it's changed from the swatch on each row of the folder window, which posts `set_folder_color` — the swatch posts in the background (AJAX) and recolours in place, so the manager stays open. Adding, removing and choosing the default happens in `render_folder_modal()` — the window that dropdown row opens — which posts the ordinary `add_folder` / `delete_folder` / `set_default_folder` actions each page already handles, so it's plain POST→redirect, not AJAX. Deleting a folder moves its items back to `General` rather than destroying them. `folders-<user>.json` carries two prefs beside the lists, both keyed by type: `default` (where new items land while you're viewing "All") and `last` (the view to reopen on). Like every stored id they're re-validated on read, so a deleted folder silently reverts to `General` / `All`.

**Calendars.** Calendars and calendar *sets* share one list, distinguished by `type => 'set'` (`is_calset()`). Events carry a calendar id. A set may hold the partner's shared calendars as well as your own, so membership is validated against `$pickIds` (mine + shared), not `$calIds` — and because that intersection is re-run on every read, a calendar the partner later un-shares drops out of the set automatically rather than leaking. `calprefs-<user>.json` holds view prefs: `hidden_folders`, `hidden_shared_folders`, `default_cal` (which calendar new events land in when you aren't viewing one in particular) and `last_cal` (the selected calendar or set, persisted rather than session-scoped). The calendar page reads reminders, notes and events together (`kind_spec()` maps each kind to its file and its text/date field names). Adding a *reminder* from the day panel offers the reminder **groups** in the default reminders folder, never a calendar — reminders belong to a folder and a section, and a calendar id would be meaningless on one. **Mine and the partner's stay in separate pickers**, never one merged list, so whose file a new item lands in is never a guess: the add window shows a calendar dropdown per owner (`cal` / `cal_shared`) and a group dropdown per owner (`section` / `section_shared`) — up to four rows, and six once notes join in. Only the partner's carries a blank `—`; picking from either side clears the other, so exactly one owner is ever selected. A shared choice writes to *their* file (`user_data_file(..., $partner)`), validated against `$sharedIds` / `$sharedFolders` on the way in. The partner's group values carry `folder\x1Fgroup` together, since a shared reminder needs both, and `\x1F` can't survive `folder_clean()`. **The day panel groups by kind *and* owner**: one collapsible `.dp-group` per pair, mine before the partner's, within the legend's kind order — "Events" then "Aki's events", and so on. `gkey()` (`kind` + `:owner`) is both the grouping key and the `localStorage` fold key (`calFold_<gkey>`), so folding "Aki's events" doesn't fold mine. The partner's headings are a shade dimmer; their rows carry no name chip any more, since the heading above already says whose they are. **Week mode** is a swipe up on `.cal-top`: the server still renders the whole month, but each cell carries `data-week`, so the mode is only a class hiding the other rows (plus the legend and the calendar picker), and the arrows step one week at a time, crossing into the neighbouring month with `?wk=first|last`. It sticks in `localStorage` under `calWeekMode`. A firm *sideways* swipe on `.cal-top` steps a whole month (left forward, right back), sharing the same `touchend` as the week-mode up/down swipe. A month cell draws one dot *per event*, first and in the calendar's colour, then at most one dot for reminders and one for notes — the counts are meant to read as "how much is on", and a long reminder list mustn't crowd the events out. The single reminder dot takes the worst state of the day: overdue beats open, and it only greys out (hidden unless Completed) once every one of them is ticked.

**The iOS widget** (`public/calendar/feed.php`) serves JSON to a Scriptable script, authenticated by a token in `token-<user>.json` rather than a session. The setup page bakes the calendars you're currently viewing into the generated URL as `&cals=<ids>` (or `cals=all`), so a widget keeps showing what you picked when you made the script — copy it again to re-point it. `feed_scope()` honours that pin (validated against your own calendar ids, so it can only ever narrow), and falls back to re-deriving the view from `calprefs` (`last_cal` + `hidden_folders`) when there's no pin or the ids are stale — which is also what older scripts without the parameter do. Reminder folders are never pinned; they always follow `hidden_folders`. It re-implements the file paths and filtering by hand — changes to how items are selected need making in both places. **Notes never reach the widget**: `build_feed()` only emits reminders and events, dropped server-side rather than only in the generated script so a widget still running an older script stops showing them too. A reminder draws an **empty tick box** (`SFSymbol.named("square")`, tinted overdue-orange when rolled) where an event draws a dot, and carries its `id` so the row can link to `quick.php?tick=<id>`. Tapping the widget opens `public/calendar/quick.php`, a session-authenticated one-field page that appends a reminder or event for today (defaults `folder => General`, `section => ''`) — it also hand-builds its rows, so a new required field on reminders or events needs adding here too. `?tick=<id>` puts it in a second mode: that one reminder with a single **Done** button, whose POST (`action=tick`, CSRF-checked) marks it done or, for a repeat, rolls it to the next date via `repeat_next()`. The tick deliberately happens *there* rather than behind the feed's token, so the read-only-token rule above still holds.

**Token auth.** Anything that can't hold a session — the Scriptable widget, the watch app — authenticates with the string in `token-<user>.json` instead. `token_user($dir, $token)` (`lib/auth.php`) does the lookup for all of them; `feed.php` still owns *making* the token, on the widget setup page. The token is a **read** credential and has been handed out as one, so nothing behind it may write: an endpoint that accepted a POST would silently give that power to every script already carrying a copy.

**The iOS and watch apps** live in `ios/` (see `ios/README.md`) and are never deployed — `deploy.sh` only sends `public/` and `lib/`. They are **completely independent of the website**: a fully native SwiftUI app with no web view, no login, no token and no network. All data is local — one `Codable` tree (`AppData` in `ios/Shared/Model.swift`) saved to a single `suite.json` in Application Support through `Store` (`ios/Shared/Store.swift`). Reminders, Calendar, Notes (plain text) and Habits are reimplemented natively, reusing the suite's ideas (folders/groups, repeats with month/year clamping, undated-first ordering, the slash-only US-order parser in `ios/Shared/Parse.swift`, two-press delete). The app starts empty. The watch is read-only: the phone builds a `WatchList` (`Store.watchList()`) and ships it over WatchConnectivity as the application context; the watch decodes and draws it. It's a separate codebase from the PHP suite — the two look alike but nothing is shared, so editing one never touches the other. `public/api/reminders.php` and the widget's `feed.php` still exist for the *web* widget/Scriptable use.

**Aki's Bookshelf** (`public/akisbookshelf/`) is a standalone app, not part of the tab bar: it gates on `current_user() !== 'aki'` after the shared login and renders its own chrome. Books come from the Open Library search API via `http_get()` (an 8-second `file_get_contents` with a User-Agent, the suite's only outbound HTTP). `book_cover()` prefers the locally cached `covers/<id>.webp` and falls back to `covers.openlibrary.org` — that cache is generated server-side and gitignored, so locally every cover comes from the network. Per-book notes are a sectioned list like the rest of the suite (`booknotes-<user>.json`). Folders are a Library-only idea here — the tiles a book's Goodreads shelves become; the book's own page has no folder controls. Its header follows the suite's: `books_header($title, $withEdit)` puts the Edit pencil beside the username at the same size, and edit-mode-only controls (like **Set cover**, which sits right of the book's details and level with the middle of the cover) hide behind `body.editing` as everywhere else.

## UI conventions

Dark theme throughout: `#111` background, `#eee` text, `#34d399` accent, pill-shaped controls. Reminders/events/notes have one palette suite-wide — `kind_color_css()` in `lib/util.php` emits it as `--k-reminder` / `--k-event` / `--k-note` (plus `-bg`/`-soft` and `--k-overdue`), and every dot, chip and tag reads those rather than a literal. The event blue is deliberately a blue (`#60a5fa`) and not a cyan, so it can't be read as the green at dot size; `cal_color_fix()` remaps calendars still holding the old `#38bdf8`. Shared chrome comes from `lib/chrome.php` and `lib/tabbar.php` (icon-only bottom bar). **The top bar is one row, 32px tall, in the same place in every app** (1.5rem from the top, 0.5rem of gap under its rule — the same small gap in every app), **with a rule under it**: back button and the app's name on the left; on the right, gathered by the `⋮`, the app's own title controls (the folder/calendar picker, or Habits' Edit pencil), then the settings `⋮` and the username. `render_user_menu()` takes a `$controls` slot that renders at the start of that right group — apps capture their picker HTML with `ob_start()` and pass it in. `.backbtn`, `.titlebtn` and `.usermenu .who` are sized together in `chrome_styles()`, so a new app only supplies what goes inside. Aki's Bookshelf repeats the same rules locally since it doesn't use `chrome_styles()`. Inputs use `font-size: 16px` so iOS doesn't zoom on focus. These are iOS home-screen PWAs — respect `env(safe-area-inset-*)`, and note `tabbar.php` intercepts same-origin clicks in `window.navigator.standalone` mode so links stay in the app.

**Edit mode.** Destructive controls (delete buttons, drag handles) are hidden unless `body.editing` is set. Every Completed toggle is the checked box `☑`, green when on. Reminders, Notes and the Calendar have **no Edit button at all**: you enter edit mode with a **long-press** (touch) or **double-click** (desktop) on a row or section — on a reminder that also opens its text inline, on a calendar row it opens the edit modal — and leave it by tapping empty space or pressing Escape. (Each app wires this itself, near its existing drag/inline-edit code.) Habits and the Bookshelf keep an Edit pencil of their own. Drag handles hide with `visibility: hidden`, not `display: none`, so entering edit mode doesn't nudge every line of text sideways. It is deliberately *not* persisted — every app starts out of edit mode, so opening the app or switching tabs never lands you in it. The one exception is the structural actions that POST→redirect back to the same page: they append `edit=1`, and the page turns edit on and strips the param with `history.replaceState`, so adding a folder or section doesn't kick you out. `keep_edit_script()` adds that field to any form submitted while editing; if you add an edit-mode-only action that redirects, make sure the handler carries `edit=1` through or it will silently drop the user out.

**User settings** live in the **username's own dropdown** — there is no settings `⋮` any more, and `settings_button()` is gone with it. The menu is the same two rows in every app, **Settings** then **Log out**, so preferences are always in the same place; Settings (`#setBtn`) closes the dropdown and opens `settings_modal_html/styles/script` (`lib/chrome.php`, emitted by `chrome_styles()`/`chrome_script()`; Aki's Bookshelf emits the modal and its own menu markup itself). Changing your password posts `change_password` to whatever page you're on — `require_login()` answers it and replies JSON. The **Change password** button sits on its own row (`.setpwrow`) directly under the password fields, *above* the Theme picker. The footer below is one row of three identical 40px round icon buttons, `justify-content: space-around` and all sharing the `.setact` class: **Share** (a share glyph — only when `$showShare` is passed, there's a partner, and `lib/sharing.php` is loaded, since not every app requires it), **Widget** (a phone glyph, linking to `/calendar/feed.php`; rendered in every app now rather than passed in as Calendar's `$extra`) and **Done** (a checkmark, in the accent as the primary action). The Share button opens the sharing window, closing settings first since the share modal sits a layer below. The `$extra` slot still exists but nothing uses it. Reminders' "Copy as Markdown" is *not* here — it's a share-icon button in the toolbar row, between Completed and + Section, that copies the visible list from a hidden `#shareMdText` textarea.

**Scroll position survives an action.** Every mutation in the suite is a POST→redirect→GET, which normally drops you back at the top of the page — so ticking a reminder halfway down the list used to jump. `keep_scroll_script()` (`lib/chrome.php`, in `chrome_script()`) stashes `scrollY` in `sessionStorage` on submit and restores it on the next load, then forgets it, so a fresh visit still opens at the top. It hooks the `submit` event *and* patches `HTMLFormElement.prototype.submit`, because a programmatic `form.submit()` (the Calendar day panel's tick box and quick delete) fires no submit event at all.

**Swipe a row left to delete it** (`swipe_delete_styles()` / `swipe_delete_script()` in `lib/chrome.php`) — the way to delete one reminder or one day-panel item without turning edit mode on for the whole list. Mark the row `swipe-row` and give it a `needs-confirm` delete control: the gesture adds `swiped`, which reveals that control, and the swipe counts as the first press so it deletes on one tap. It stands down in edit mode, where dragging owns the row.

**Deleting is a two-press gesture** (`confirm_delete_styles()` / `confirm_delete_script()` in `lib/chrome.php`) — there is no `confirm()` box and no Undo button anywhere. Give the control class `needs-confirm`: the first press fills it red — the label never changes, since a `×` that became the word `Delete?` resized its row — and the second submits and the script injects a hidden `confirm=1`. Server handlers must require `!empty($_POST['confirm'])` before destroying anything, so a stale page can't delete on one tap. Pages that don't use `chrome_styles()`/`chrome_script()` (e.g. Aki's Bookshelf) emit the two helpers themselves.

**A row of buttons is one size.** Where several sit together — the Calendar's `Completed / + Add`, Reminders' `Completed / (share) / + Section`, Notes' `+ Section` — they share a height (32px) set on the row, not per button. `+ Section` is a button that swaps itself for the name field when pressed and swaps back if you leave it empty; the field and its `+` take that same height. Labels are short — `+ Note`, `+ Section` — not `+ New …`. A section header's `×` is pushed right with `margin-left: auto` and the header carries the rows' side padding, so it lands under the rows' `×`s.

The Calendar's day-panel buttons are the reference for button sizing across the suite: `padding: 0.35rem 0.9rem; font-size: 0.9rem; border-radius: 999px`, green (`#34d399` on `#06251b`, weight 700) for the primary action and outlined (`1px solid #333`/`#444`) for the rest. Manager windows (calendars, folders) share one shape too: `<h2>`, an add row with a green `+`, a list of rows each with an `×`, then a Done button. The Calendar manager's three parts (Calendars, Calendar sets, Reminder folders) are collapsible `.cm-section`s — tap the `<h2>` to fold one, remembered in `localStorage`.

## Working here

- Commit granularly and deploy promptly; committing straight to `main` is fine.
- Match the existing style: procedural PHP, short helper functions with one-line docblocks, `e()` for escaping, inline `<style>`/`<script>` in the page.
- To exercise a page without credentials, drive it from the CLI: start a session, set `$_SESSION['auth']`/`$_SESSION['user']`, set `$_SERVER['REQUEST_URI']`, then `require` the page. That renders (or POSTs to) it exactly as the server would, and it's the fastest way to check a change end-to-end.
